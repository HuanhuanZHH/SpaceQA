# SpaceQA 项目结构与阶段交接讲稿

以下讲稿与《项目结构与阶段交接总结_20261108.md》中的三张 Mermaid 图对应。每段约 300 字，可直接用于路演、阶段汇报或录屏配音。

## 讲稿一：总体系统结构图

这张图展示的是 SpaceQA 从数据进入到报告输出的完整链路。系统接收一个数据包目录，或者接收包含多个数据包的 publish 根目录。第一步不是直接调用模型，而是先建立样本清单，识别 AIA、HMI、CME、EPB、DMSP 和 ULF 六类数据，把图像或 CSV 与 JSON 标注逐条配对，同时记录文件版本、哈希、尺寸、时间字段和同源样本关系。完成登记后，数据进入两条并行路径：一条是确定性规则检查，负责发现文件缺失、标签孤儿、尺寸矛盾、字段冲突和时间格式问题；另一条是模型输入准备，生成图像与标注对照视图、波形和结构化特征。规则结果可以直接形成确认问题，模型结果先作为带概率的候选。两类结果在质量台账中合并，但状态始终分开保留。最后，程序计算六维技术观测、八类污染指数和全局排序，并输出评分卡、问题清单、证据索引和运行日志。这样做的重点是让每个结论都能回查到原文件、样本、标注记录或图像区域。

## 讲稿二：后端结构与调用关系图

这张图说明系统后端如何支撑网页和对话式工作台。用户可以从主控制台、对话页面或兼容的 evaluation.html 进入，前端请求统一交给 web_service.py 和 chat_service.py 处理。服务层负责上传任务、历史运行、案例查询、报告读取和追问，不直接修改原始数据。任务进入队列以后，由 engine.py 执行清单建立和规则检查，再由 audit.py 独立读取产物并复算证据、评分和排序；priors.py 提供当前数据的先验观测，quality_ledger.py 管理通过、不通过、待判定和不适用四种状态，refinement.py 与 review_mcp.py 负责需要人工或独立参考的细分复核。所有模块都把结果写入同一运行目录，评分卡、排序表、问题清单、证据索引和运行日志保持同一个 runId、规则版本和随机种子。对话模块可以把结果组织成摘要，也可以调用 DeepSeek 或 Qwen 解释接口，但大模型只负责语言组织，不改变问题状态、污染指数、分数或排序。因此系统既能像聊天工具一样交互，也保留了离线、可审计和可复算的后端主线。

## 讲稿三：模型与融合结构图

这张图展示的是模型层如何从多个角度判断同一个样本。图像数据会进入 Qwen3-VL-8B-Instruct 视觉语言专家、监督训练的 CNN 学生、蒸馏学生、剪枝恢复学生，以及 U-Net、Attention U-Net、U-Net++、YOLO、DINOv2 和 I-JEPA 等视觉专家；结构化字段和时间序列则进入 GBDT 先验专家。当前默认方案保留 21 个基础专家，每个专家先输出几何与覆盖、数量、类别与参数三组概率，共得到 63 维专家信号。系统再把这些概率、结构字段、数据类型编码和规则标记送入 HGB7 融合器，由三个分类头综合判断。为了支持更细的缺陷分类，我们又设计了八头 HGB7、八头 HGB15 和轻量结构特征分支，并按验证集中的数据类型与缺陷类别冻结选择。定位分支负责生成框、掩膜、记录指针或时间区间，随后与当前标注进行匹配，形成漏标、虚标、边界和覆盖候选。模型负责发现疑点，规则和证据负责确认，评分程序负责最终计算，避免把模型概率直接当成科学真值。

## 讲稿四：数据处理与样本分组原理

系统处理数据时，首先把文件关系转换成可追踪的样本记录。对于图像数据，记录原图路径、标注路径、图像尺寸、标注对象数量和类别；对于 ULF，记录 CSV 字段、采样率、时间列、事件区间和参数单位。每条记录都有数据哈希和标签哈希，能够判断运行期间源文件是否被替换。P0 到 P4 不是五个互相独立的数据集，而是同一原始样本的不同质量档位，因此系统使用 base_sample_id 把它们归并，再使用 split_group_id 合并重复内容。训练、验证和测试以组为单位划分，确保同一原始样本的不同档位不会泄漏到不同集合。对于缺失文件、无法解析的标签或路径错误，系统不会删除记录，而是把预期路径和异常状态保留在清单中。这样，后续的统计分母、问题计数和审计报告都建立在完整登记数据上，而不是只对成功读取的文件进行选择性统计。

## 讲稿五：八类问题识别原理

目前系统把内容问题拆成八类：数据文件缺失、边界与位置偏差、类别标注错误、起止时刻偏差、元数据尺寸矛盾、漏标、虚标以及覆盖不足或覆盖过度。文件缺失、尺寸矛盾、字段冲突和时间格式错误，优先由规则直接检查，因为这些问题有明确的文件或字段证据。边界、漏标、虚标和覆盖问题需要模型生成候选区域或时间段，再和当前标注进行一对一匹配。比如模型发现一个可信目标，而 JSON 中没有对应对象，可以形成漏标候选；但模型没有发现目标，不能单独证明当前标注是虚标，所以系统会保留复核状态。每条问题都记录缺陷代码、概率、定位方式、影响范围、证据引用和状态。一个样本可以同时存在多个问题，因此八类数量不简单相加。没有独立参考答案时，系统仍可输出候选、污染指数和定位证据，但不会把这些结果包装成官方 Precision、Recall 或 F1。

## 讲稿六：评分、污染指数与排序原理

系统把评分分成六维技术观测和八类污染指数两部分。六维包括完整性、标注质量、样本对应、覆盖与分布、文档与来源追溯、使用条件。每一维都记录适用检查数、通过数、失败数和未决数，技术观测按照已完成且可核验的检查计算，缺少材料时不自动补零，也不自动补满。八类污染指数则对每个缺陷类别统计超过阈值的样本概率贡献，规则确认的问题在诊断统计中按概率一计入。总污染指数是八类贡献之和，数值越低表示发现的问题风险越小，数据包按总指数升序排列。评分卡还会展示主要缺陷、影响范围、样本数量、证据覆盖率和回查入口。需要强调的是，污染指数是系统对当前输入的风险观测，不等于真实污染率；正式的精确率、召回率和 F1 仍需外部参考答案。排序、分数和报告全部由确定性程序生成，模型只提供候选信号和定位依据。

## 讲稿七：证据、审计和大模型原理

SpaceQA 的结果不是只给一个分数，而是同时输出可复核的证据链。每条问题会关联样本 ID、缺陷代码、文件路径、JSON Pointer、图像框或多边形、时间区间、输入哈希、规则版本和运行日志。审计器会重新读取这些产物，检查引用是否存在、哈希是否一致、排序是否连续、评分是否可复算。对需要人工复核的案例，系统要求两名独立复核者分别提交判断；类别、位置、源文件版本不一致时，结果保留为未知或转仲裁，不会自动生成负样本。大模型接入后，输入可以包括图像、标签、专家概率和已有证据，输出按照固定 JSON 结构给出细分问题、位置、程度和解释。它的作用是把复杂证据组织成人能读懂的说明，或者帮助规划下一步检查；它不负责替换规则确认，也不负责直接修改分数和排序。这样既能利用大模型的语言和视觉理解能力，又能保持正式结果的可审计性。

## 讲稿八：当前完成情况与后续问题

目前已经完成了系统架构梳理、数据配对和哈希登记、规则扫描、八类问题账本、六维评分、污染指数、全局排序、证据索引、对话工作台、案例核查页面和复核协议。仓库回归测试为 238 项全部通过，4 项因 Windows 软链接权限或可选 SciPy 条件跳过；复核协议和新增后端策略测试均已通过，源码快照验证也已经完成。已有历史记录显示 0.6.0 压缩镜像约 19.748 GB，A100 上的历史全量专家前向约 52.1 分钟。后续需要完成的是指定 A10 硬件上的端到端耗时和显存收据、最终 PDF 和镜像提交包、演示视频、干净 Windows 客户端验收，以及正式输入上每个专家独立前向的哈希和资源记录。路演或隐藏数据集没有独立缺陷真值，这是外部数据条件；系统本身已经提供候选输出、定位字段、污染指数、评分卡和复核接口，待参考答案提供后即可通过现有审计程序计算正式指标。
